## 1. P0-A 判定口径：补第三类

### 问题

`aggregate.ts` 原来只有两类：项目缺陷 / 工具性失败（7 条模式）。
「Sentinel 自己拼出一个不存在的 URL，于是 404 了」两边都不属于 —— 它被判成**项目缺陷**，
于是每次 run 都产假 P1，CI 被拉红（`run.ts` 原来 `filter((b) => !isToolFailure(b))`）。

### 改法

新增第三类 `sentinel-invalid-url`，判据三条同时成立：

1. 只有 404，**没有** 5xx / console error（否则是真缺陷）；
2. 出问题的地址带**路由占位符**（段级判定：`:id` 动态段 / `:slug*` 捕获段 / `@slot` 并行槽漏网）；
3. 也就是说：**这个地址本来就不存在，是 Sentinel 自己拼错的**。

> 刻意**不**把所有 404 排除 —— 分析文档 P0-A 明确要求过。
> 也刻意不认 `(` `)` `[` `]`：Pages Router 的目录名就是 URL 段
> （`pages/(marketing)/about.tsx` 的真实地址是 `/(marketing)/about`，Next.js 官方文档如此），
> 那是**真实路由**，它 404 了就是项目的问题。

出口一致：`classifyBug()` 是唯一判定入口，报告、JSON、退出码、`run-status.json` 全部调它。
`run-status.json` 新增 `toolFailures` / `sentinelInvalidUrls` / `projectDefects` 三个计数。

### 验证

`packages/reporters/test/verdict.test.ts`（12 例）：工具故障 / 自造地址 / 真实地址 404 / 500 误判防护 / 端口号不算占位符 / 报告横幅 / JSON 字段。

## 2. P0-B 证据链：空壳 / 截断 / 丢弃

### 2.1 `dom-snapshot` 是空壳 → 真的有生产者了

`runner.ts` 原来在类型里声明了 `domSnapshot?: string`，**没有任何一处把它 push 进证据链**。
现在失败路径会把它变成真正的 `dom-snapshot` 证据（超 20 000 字符时写明截断）。

### 2.2 截图：模型看不到 → 落盘成真实文件 + 如实说明

- 截图从「base64 data URI 塞在证据里」改成**落盘成 `reports/evidence/shot-<hash>.png`**，证据里给的是文件路径；
  落盘失败才退回内联 data URI（证据不能因为存不下文件就整个丢掉）。
- `formatEvidence` 不再把它换成 `[image data; inspect separately]`（那句等于"证据在手上"，实际模型一个字都看不到），
  改成如实说明：**当前模型通道只支持文本，模型未对该图做视觉判读**。

> **为什么没让模型真的看图**：`core/ports.ts` 的 `ChatMessage.content` 是 `string`，
> 要支持图片必须改 core 端口（宪法红线 3「子代理升级不能改 core」，且 core 已 491/500 行）。
> 本轮不做，如实标注限制。

### 2.3 a11y 树被从尾部砍断 → 保头保尾 + 写明截断

原来 `JSON.stringify(detail).slice(0, 4000)` —— 超过 4000 字符的 aria 树**尾巴直接没了**，
模型拿到半棵树却照样下根因断言。现在按类型处理：a11y 保头保尾并写明"中间省略了多少字符"，
DOM 保头部并写明总长度，普通证据同样保头保尾。

### 2.4 报告层看不到内容 → 给可读预览

`a11y` 以前只显示字面量 `accessibility tree`，`dom-snapshot` 只显示 `DOM (N chars)`。
现在给前几行 a11y 预览 / DOM 标签骨架（完整内容仍在 JSON 报告里）。

### 2.5 `bug.rejected` 不拦截 draft → 现在真的拦

- `critic.ts` 的拒绝载荷带上性质：`insufficient-evidence`（真判定证据不足）/ `unavailable`（critic 自己没跑起来）。
- `collect.ts` 的收集器新增 `onRejected()`：
  - 证据不足 → **从发现列表剔除**（并把该 flow 移出"已被诊断覆盖"，失败流程回到"未解决"）；
  - critic 没跑起来 → **保留发现**（没人验过 ≠ 假设不成立），报告里标明"未经反向验证"。
- **顺序陷阱已处理**：bus 是顺序 await 分发，critic 的处理函数比收集器先跑，
  所以"拒绝"事件可能**先于**"草稿"到达 —— 收集器按 id 记住拒绝状态，草稿到达时再决定收不收。
- 报告新增「被 Critic 拒绝的假设」区块 —— 剔除不等于藏起来。

### 2.6 附带：规则类观察项不再进 LLM critic

`inspector` 发的确定性观察项（缺 viewport / 缺 lang 之类）本来也进 critic，
于是每条都被判"证据不足"、每次都白花 token、run-status 里堆一堆噪音。
现在 `origin === 'rule'` 的草稿不进 critic（它们是运行时事实，不是根因假设）。

### 验证

- `packages/subagents/test/evidence-format.test.ts`（5 例）：a11y 头尾都在、截断写明、截图不再有占位串、DOM 截断标注、文件证据尾部保留。
- `packages/subagents/test/runner-evidence.test.ts`（3 例）：DOM 真的进证据链、截图真的落盘成 PNG（校验 PNG magic bytes）、没有目录时仍留证据。
- `packages/subagents/test/critic-rejection.test.ts`（3 例）：两种拒绝性质区分、规则观察项不进 critic。
- `packages/reporters/test/collector-rejection.test.ts`（6 例）：先拒后收 / 先收后拒 / flow 覆盖状态 / 未验证保留。

## 3. P0-C 路由约定：先判 router，再套约定

### 官方语义（本次以 Next.js 官方文档为准逐条核对）

| 约定 | App Router（`app/`） | Pages Router（`pages/`） |
|---|---|---|
| 路由组 `(group)` | 不进 URL，不算路由段 | **没有这个约定** —— 目录名就是 URL 段 |
| 并行槽 `@slot` | 渲染在父路径上，不算路由段 | **没有这个约定** |
| 拦截路由 `(.)x` `(..)x` `(...)x` | `(.)` 同级 · `(..)` 上一级 · `(..)(..)` 上两级 · `(...)` 从根目录起 | **没有这个约定**（Parallel/Intercepting Routes 是 App Router 专属） |
| 动态段 `[id]` | `:id` | `:id` |
| 捕获段 `[...slug]` / `[[...slug]]` | `:slug` / `:slug*` | `:slug` / `:slug*` |

来源：Next.js 官方文档 Intercepting Routes / Route Groups / Pages Router 的 Pages and Layouts、Dynamic Routes。

### 改法

`nextjs.ts` 重写：段名解析集中在一处，**按 router 类型分别套约定**（`parseSegment(name, mode)`）。
并行槽产出的路径只有在**同一路径另有真实页面**时才保留（否则 `/` 会被一个孤零零的 modal 槽凭空造出来）。
最终路径去重（页面 / API 各自去重）。

顺带修掉一个 worker 报出的相邻问题：Pages Router 的 API 判定从 `startsWith('/api')`
改成边界判定（`/api` 或 `/api/`），否则 `/apixyz`、`/api-docs` 全被当成 API。

### 验证

- `packages/adapters/test/nextjs-routes.test.ts`（11 例）：App / Pages **两套独立夹具**，逐条断言约定。
- `packages/subagents/test/mapper.test.ts` 新增端到端用例（分析文档 §4.2 的要求）：
  **路由解析与 `isConcretePath` 必须一起对** —— 断言自动流程里不出现 `@` / `[` / `]` / `(.)`，
  真实路由照常被测，动态路由不进流程但在覆盖缺口里说清楚。

## 6. 第二轮（2026-10-29 晚）：相邻问题 + P1-3 视觉链路

> 一句话结论：把上一轮欠着的三笔账结了 —— 任意目录的 `route.ts` 会被漏掉、
> API 的真实 HTTP 方法测不出来、`basePath` 前缀不认识；
> 以及**模型现在真的能看到截图**（但要显式开 `vision`，默认关）。

### 6.1 适配器增强（`packages/adapters/src/frontend/nextjs.ts`）

| 改动 | 为什么 | 官方依据 |
|---|---|---|
| **任何目录下的 `route.ts` 都是 API 端点**（原来只在 `api/` 树收集） | `app/users/route.ts` 定义的 `/users` 端点以前根本不会进 API 清单 → 覆盖率虚高、契约校验无从谈起 | Next.js Route Handlers：`route.js/ts` 文件即端点，与目录名无关 |
| **从 `route.ts` 源码解析真实 HTTP 方法**（`export async function POST` / `export const POST` / `export { GET, POST }`），一个方法都没写时默认 GET | 以前所有 API 都记成 GET，POST 端点被当 GET 测 | Next.js 约定：`GET`/`POST` 等由具名导出决定 |
| **读 `next.config.*` 的字面量 `basePath` 并给所有路径加前缀** | 站点挂在 `/app` 子路径下时，我们拼的地址全部少了前缀 → 全部 404，**正是第三类判定要掩盖的那种假失败** | Next.js `basePath` 配置项 |

> `basePath` 只认**字面量**（`basePath: '/app'`）。写成变量（`basePath: process.env.X`）时**不猜** ——
> 猜错前缀比不处理更糟：会产出一批访问不到的伪路由。`rewrites` / `redirects` 同理不做静态解析
> （它们的语义依赖运行时文件系统，静态解析不可靠）。

新增测试 5 例（`packages/adapters/test/nextjs-routes.test.ts`）：任意目录 `route.ts` ·
具名导出的 POST · 多方法导出 · `basePath` 前缀 · 变量形式 `basePath` 不猜。

### 6.2 P1-3：让模型真的看到截图

**改前**：截图 = 证据里的一个路径字符串；模型通道只认文本；
analyst 只能如实写"模型未对该图做视觉判读" —— 诚实，但最有信息量的现场被挡在模型之外。

**改后**（`vision` 开关**默认关**，理由见下）：

```
截图 PNG（落盘）→ analyst 读盘 → base64 → ChatMessage.images
   ├─ openai-compatible：content: [{type:'text'},{type:'image_url',image_url:{url:'data:image/png;base64,…'}}]
   └─ ollama-native    ：messages[].images: [base64]
```

| 环节 | 落地位置 |
|---|---|
| 端口扩展（core +3 行，494/500） | `ChatMessage.images?: ContentImage[]`、`LLMProvider.supportsVision?: boolean`、`ContentImage` 类型 —— 都是**可选**的，老 provider 与老测试桩一行不用改 |
| OpenAI 协议转换 | `packages/providers/src/llm/openai-compatible.ts`：`vision: true` 时按官方 `image_url` 数组格式；关闭时图片被忽略（不发也不报错） |
| Ollama 原生转换 | `packages/providers/src/llm/ollama-native.ts`：走原生 `images` 字段（base64 数组），不是 OpenAI 那种 content 数组 |
| analyst 附图 | `packages/subagents/src/analyst.ts`：`collectVisionImages()` 读盘 → base64；**只有真的附上了图**，文字描述才改成"已作为图片随本条消息附给模型"，否则仍如实写"模型通道只支持文本" |
| 开关 | `llm.yml` 的 provider 新增 `vision` 字段（`init` 模板 / `CONFIG-SPEC.md` 同步），默认 `false` |

**三条边界（都是有意为之）**：

1. **默认关闭** —— 截图是本机现场内容，发给模型等于**传出本机**，必须用户显式同意；
   而且不少模型收图片会直接报错（整轮 run 挂掉）、图片 token 也贵。
2. **最多 3 张、单张 ≤5MB** —— 防止一次请求把 token 预算打爆。
3. **读失败就跳过，不报错** —— 截图读不出来不该让整轮 run 挂掉（证据与 draft 照常产出）。

**顺带修掉的一处隐性失真**：`llmConfigToYaml` 现在会把 `vision` 写回去 ——
以前"用 Web Settings 存一次配置"会把这类开关悄悄抹掉，用户以为截图已经给模型了，
实际一直在走纯文本通道（与 v1.4 记的 `pricing` 被抹掉是同一类缺陷）。

**core 改动怎么合规**（红线 3 的执行口径，本次已写进宪法 v1.6）：
子代理的**逻辑**升级不许改 core；新增 provider 能力只能以**可选端口扩展**落地，
且不破红线 1（core 不依赖任何实现）、不破红线 2（494/500）。
逐条处置见 `CONSTITUTION-CHANGES.md` 的 v1.5 → v1.6 一节。

新增测试 12 例：
`providers/test/openai-compatible.test.ts`（+5：supportsVision 如实暴露 / image_url 格式 /
关闭时忽略图片 / system 消息不带图 / 图片 token 计入估算）·
`providers/test/ollama-vision.test.ts`（新，2：images 字段 / 关闭时无 images）·
`subagents/test/analyst-vision.test.ts`（新，5：data URI 拆分 / 落盘文件读出 /
不支持视觉时不附图 / 读失败不挂 / 最多 3 张）。

## 7. 第三轮：P1-G 限流（宪法硬条款）+ P1-E 聚类与证据去重

> 一句话结论：宪法里"每次 run 触发检索的流程占比 ≤30%"从**自觉**变成了**可核对的事实**
> （实现 + 守卫 + 统计三件套）；重复结论从"症状全文精确匹配"改成**相似度聚类 + 证据去重**，
> 并且给出了**压缩前后的字节数**。

### 7.1 P1-G 知识增强 30% 限流

**改前**：`enhancer` 只有一条"平均置信度 < 0.7 就搜"。
置信度低的流程一多，检索就跟着涨，成本和外部服务压力都不受控 —— 而且没人查得到。
这条是**宪法硬条款**（`docs/CONSTITUTION.md` §知识增强），当时只能靠实现里的自觉。

**改法**：

| 环节 | 落地 |
|---|---|
| 计数单位 | 钉死为**流程**（`bug.affectedFeature` = flowId），同一个流程只检索一次 |
| 上限换算 | `floor(流程数 × 0.3)` —— **floor 不四舍五入**（30% 是上限不是目标）：10 流程 → 3 次，3 流程 → 0 次 |
| 分母来源 | `map.ready` 里的 `flows.length`（mapper 在所有流程开始前发出，一定是全量）；拿不到时用保守分母 10 |
| 超限不静默 | 被上限挡下来的记 `skippedByCap`，同一个流程重复触发的记 `skippedSameFlow` |
| 可核对 | `run-status.json` 新增 `knowledgeSearch`：`{totalFlows, searchedFlows, rate, cap, maxSearches, skippedByCap, skippedSameFlow}` |
| 只许调低 | CLI `--knowledge-rate <0-0.3>`，越界在入口报错（调高 = 让工具违反自己的宪法） |

**守卫**（新增 `bun run guard:knowledge`，`scripts/check-knowledge-rate.mjs`）：
从**外部**数真正的外部检索次数（不信 enhancer 自报），三条断言：

1. 10 流程 / 10 条待修复发现 → 实际检索 ≤ 3 次；
2. 3 流程 → **一次都不能搜**（floor(3×0.3)=0），但必须有"因上限跳过"的记录；
3. 计数单位是流程，不是每条发现。

**双向反证（守卫必须能失败）**：临时把 `budgetLeft` 改成 `true`（拆掉上限）→ 守卫报 **6 项失败、退出码 1**；
恢复后退出码 0。改动脚本：`packages/subagents/src/enhancer.ts` 的限流判断那一行。

> 写守卫时踩了一个测量缺陷：第一版所有 bug 用同一个方案标题 → **被知识缓存合并成 1 次**，
> 测到的"外部检索次数"少了 9 次，限流有没有生效反而看不出来。
> 改成每个流程用不同查询后才测到真实值（正好卡在上限 3 次）。

**`lint:spec` 同步加固**（原来只查"有没有限流代码"这一行正则）：

- 上限值必须还是 `MAX_SEARCH_RATE = 0.3`（被人调成 0.9 也不算合规）；
- `run-status.json` 必须有 `knowledgeSearch`（超限了要查得到）；
- 守卫脚本必须存在（守卫优先于自觉）。

`no-rate-limit` 这条**已知偏差已清零**：baseline 由 11 项降到 10 项
（走 `--update-baseline` 这条唯一合法路径，baseline 有 sha256 指纹，手改会被拒）。

### 7.2 P1-E 根因聚类 + 证据去重

**改前**：`aggregateDuplicateBugs` 按「source + severity + 症状全文**精确匹配**」分组。
抓不到"同一个错、只差一个数字/路径/时间戳"的重复 —— 而那正是真实运行里最常见的形态
（2026-06-15 一次跑出 25 条几乎相同的假阳性）。

**改法**（新增 `packages/reporters/src/cluster.ts`，`aggregate.ts` 改为调用它）：

- **归一化**剔除 TIMESTAMP / UUID / HASH / URL / PATH / NUM（≥4 位）+ 路径的"行:列"尾巴；
- **相似度** = 0.6 × Levenshtein + 0.4 × Jaccard（只看前 240 字符）+ 同错误类型加成 0.2，
  阈值 0.85（cats 的 `ErrorSimilarityDetector` 口径）；
- **两条硬否决**（顺序在相似度之前）：
  1. 错误类型不同 → 不是同一个问题（`TypeError` vs `ReferenceError`）；
  2. HTTP 状态码不同 → 不是同一个问题（500 vs 404）。
  为此归一化时**3 位状态码必须保留**（只抹 4 位以上数字）——
  否则"服务挂了"和"地址不存在"会被合并成一条。
- **包含关系规则**：短的那条是长的那条"去掉现场尾巴"的版本时判为同一个
  （"同一个错、不同行号"光看字面相似度只有 0.81，掉到阈值以下合并不了）；
- **证据去重**：按 `kind:hash` 去重，并给出 **beforeBytes → afterBytes** 量化
  （midscene 的 compactor 口径）——"变简洁了"必须变成可比的数字。

**接进报告**：Markdown 报告多一行「**同源合并**: N 条重复发现已合并（剩 M 组）；证据去重 X 条 → Y 条（A → B 字节）」；
JSON 报告多一个 `dedupe` 顶层字段；`run-status.json` 同样带上，机器可核对。

新增测试 14 例（`packages/reporters/test/cluster.test.ts`）：归一化 / 状态码保留 / 错误类型键 /
相似度两个方向（该合并的合并、不该合并的不合并）/ 聚类的四条硬过滤 / 证据去重与量化。
